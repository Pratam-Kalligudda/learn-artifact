01 The PLC

Not a computer running a program — a runtime with one job, executed on a fixed budget, forever.

A Programmable Logic Controller doesn't run code the way a server does. There's no event loop waiting on something to happen. Instead it runs a scan cycle: read every input, evaluate the whole program once against that snapshot, write every output, do a bit of housekeeping (comms, diagnostics), and start over — whether or not anything actually changed. A cycle typically takes 1–50ms depending on program size and PLC class, so from the outside it reads less like a stream of change events and more like a steady heartbeat.

Fig. 1 — the scan cycle: the loop every PLC runs, regardless of brand.

The logic itself is usually written as ladder logic — rungs that look like relay wiring diagrams, read left to right — because it maps directly onto the electromechanical relay panels PLCs replaced. Brand doesn't change the model: a Siemens S7-1200, an Allen-Bradley CompactLogix, and a Mitsubishi FX all run the same read → execute → write loop underneath their own tooling.

IT translation

Closer to a fixed-tick game loop than a request handler — it doesn't wait for input, it polls the world at a guaranteed rate and never skips a beat.

02 Sensors & motors, as the PLC sees them

Zoomed out past the wiring — for this flow, they're just addresses the scan cycle reads and writes.

The wiring, signal conditioning, and scaling are a separate topic. What matters here: by the time a value reaches the program, a sensor is a discrete bit or a scaled number sitting at an input address, and a motor is a bit or setpoint the program writes to an output address. The PLC already did the hard part — debouncing a switch, linearizing a 4–20mA loop into engineering units — so what you eventually see is a clean, named tag with a value and a timestamp, not raw voltage.

Fig. 2 — field devices resolve to plain addresses in PLC memory; the PLC never touches motor current directly, a Variable Frequency Drive (VFD) does that.

One distinction worth keeping: the PLC doesn't power the motor — it tells a VFD what to do (run, stop, target speed), and the drive handles the actual current. That's why a motor "reading" you see later is almost always a commanded setpoint or a drive-reported speed, not a raw electrical measurement.

03 Protocol landscape

How the PLC's memory gets onto a wire, and who's allowed to ask for it.

None of these are fixed to your site yet, so treat this as the field guide: five protocols you'll run into, what pattern each one follows, and where it usually sits in a plant.

ProtocolPatternTransportWhere it livesThe one-liner
Modbus poll master/slave RS-485 (RTU) or TCP/502 Legacy PLCs, drives, meters Raw register reads, no names, no schema, no auth. Everywhere because it's trivial to implement.
OPC-UA client/server browsable TCP/4840, TLS optional PLC ↔ SCADA / edge gateway Closest thing OT has to a typed API — nodes carry names, types, and metadata, not just numbers.
MQTT pub/sub via broker TCP/1883 (8883 TLS) Edge gateway → cloud The pattern you already know from IT — usually the last hop before your ingestion pipeline.
PROFINET cyclic RT real-time Ethernet Ethernet, EtherType 0x8892 Siemens-heavy machine level Built for millisecond determinism between PLC and drives — rarely leaves the machine.
EtherNet/IP producer/consumer CIP TCP/UDP 44818, I/O UDP 2222 Rockwell / Allen-Bradley plants Same real-time goal as PROFINET, different vendor ecosystem (CIP over Ethernet).
Where the gateway fits

Your edge gateway's whole job is to speak whichever of these dialects the PLC speaks on the floor side, and re-publish it as the one dialect your pipeline speaks on the other side — almost always OPC-UA in, MQTT out.

04 Edge gateway

The translator between however many PLC dialects are on the floor, and the one your pipeline expects.

Kepware (KEPServerEX) is an OPC server: it ships with drivers for the protocols above — Modbus, PROFINET, EtherNet/IP, Siemens S7, dozens more — and re-exposes every one of them as a single, consistent set of OPC-UA tags. Point it at ten PLCs from five vendors and it hands back one uniform namespace, regardless of what each PLC actually speaks natively.

Node-RED typically sits right after it: a flow-based tool that subscribes to those OPC-UA tags (or polls Modbus directly when there's no OPC server in the way), reshapes and filters the values, and publishes them onward — usually over MQTT — to whatever's listening next.

Field glossary

Tag
a named, typed data point exposed by the PLC or gateway — what "%IW4" becomes once it has a human-readable name.
Register
a fixed-size memory slot the PLC exposes for a value; Modbus addresses these directly, e.g. holding register 40001.
Polling vs. subscription
Modbus clients ask "what's the value now?" repeatedly; OPC-UA/MQTT clients get told when it changes.
Fieldbus
any of the wire-level protocols connecting PLCs to drives/sensors at the machine level (Modbus, PROFINET, EtherNet/IP).
Historian
a time-series store built for plant tags — the OT-side ancestor of what TimescaleDB does downstream.
IEC 61131 addressing
the %I0.0 / %Q0.0 notation: input/output, byte, bit.
